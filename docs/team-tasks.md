## 2 架构与依赖方向

```text
  python main.py ──无参数──► gui/ (Tkinter)           web/ui ◄── web/runtime（Pyodide Worker）
       │ play / validate / replay / graph   │                              │
     cli.py ◄─ parser.py                     └──► session_factory.create_session ◄──┘
       │                                                   │
       │                            legacy_session.py（临时）→ session.py（ZQO）
       └──────────────────────► engine.py ◄────────────────┘          ← ZQO
                                 │      │
                           rules.py  state.py   mechanics/base.py     ← ZQO
                                 │                 ▲          ▲
                                 │        mystery.py      puzzle.py   ← ZC / ZRS
                                 ▼
          model.py ◄── loader.py   validator.py   walk.py             ← YHT
                         ▲
                 stories/*/story.json（剧本数据）                       ← ZC / LQ
          save.py（编码与校验）──► SaveStore：桌面文件 / web/storage    ← LQ
```

依赖只向下：展示端（命令行、桌面、网页）只通过会话接口或引擎访问游戏，引擎调用规则与插件，所有模块共享 `model.py` 与 `ui_contract.py` 的数据类型。引擎、插件与会话不依赖 Tkinter、DOM、浏览器存储或 Cloudflare，不调用 `input`/`print`、不读写文件，所以能在单元测试和浏览器中直接驱动。接口细节见 [接口约定](contracts.md)。

## 3 为什么五个人可以同时开工

上一个项目（SkyRoute）按棒次串行，后一棒要等前一棒合入。本项目改为**契约先行、并行开发**：

1. **v0 骨架已就绪**：仓库里已有可运行的最小引擎、两个剧本序章和 94 项测试，CI 全绿。每个模块都有能用的最小实现，没有“等别人先写完”的空接口。
2. **接口冻结在 `model.py` 和 `engine.Engine` 的公开方法上**。修改接口走 contract PR（[接口约定](contracts.md) 第 5 节），其余代码各改各的文件，不会冲突。
3. **测试互不牵连**：各模块测试只用 `tests/fixtures.py` 里的迷你剧本，不读真实剧本。剧本作者改剧情不会让别人的单元测试失败；剧本是否能通关由 `tests/integration/` 统一检查。
4. **CI 按成员分项显示**：PR 页面上 `tests (yht)`、`tests (zrs)` 等分项显示结果，一眼看出是哪个模块出错；网页构建与浏览器测试单独显示为 `web` 检查。

GUI／网页采用 `taleloom/ui_contract.py` 的明确接口。界面可使用 `tests/ui_fakes.py` 的测试替身；引擎组独立实现会话适配器；存档组实现存储接口。测试替身仅供开发，不代表引擎适配已经完成。

每人本地跑自己的模块测试，提交前再跑全量测试：

```bash
python -B -m unittest discover -s tests/<缩写小写> -t .
```

## 4 各成员任务（模块阶段，只含代码）

每项任务按“先写会失败的测试，再写实现”（课件 V 模型 / TDD）完成，测试名称写清楚验证的行为，最终合并时据此统一整理需求表。“必做”是满足课程“优良/卓越”所需的代码；“加分”在必做完成后选做。

### 4.1 YHT：剧本格式、加载与静态校验

v0 已有：JSON 加载、带位置的格式错误（如 `$.scenes[1].text: 应为字符串`）、跳转/物品/未知条件效果检查、可达性与结局检查。

必做：

1. **参数校验**：条件和效果的参数类型（如 `var` 必须是 `[名称, 运算符, 数值]`、运算符合法、`add_var` 数值为整数），错误信息指向具体位置。
2. **结构检查增强**：只能进不能出的场景（陷阱环）、`once` 选项用完后无路可走的场景、未被任何地方使用的物品（警告）。
3. **校验命令的可读输出**：错误按场景分组，给出修改建议。
4. **格式字段同步**：剧本格式新增或调整字段时，同步更新 `model.py`、`loader.py` 中的文档字符串（说明文档在最终阶段统一整理）。
5. 测试：每条校验规则至少一个通过例和一个失败例。

加分：`python main.py graph <剧本>` 导出 Mermaid 场景图；JSON 解析错误显示出错行内容。

GUI／网页新增必做：维护共享展示类型与 JSON 数据约定，新增可选素材和公开资源字段的校验，保持旧剧本兼容。已提交的加载／校验代码继续按原 PR 审阅。

### 4.2 ZQO：运行时核心与插件接口

v0 已有：状态、条件/效果注册表、选择与跳转、一次性/条件选项、每回合效果与触发器、跳转循环检测、插件动词分发。

必做：

1. **文本插值**：场景文字中的 `{vars.oxygen}`、`{item:tape}` 等占位符在显示时替换，未知占位符给出清楚提示而不是崩溃。
2. **条件化场景文字**：场景可声明 `variants`（满足条件时追加或替换描述），让同一地点前后两次进入看到不同内容。
3. **可复现的随机**：`{"chance": 30}` 条件，随机种子保存在 `GameState` 中，读档和回放结果一致（LQ 的回放测试依赖这一点）。
4. **插件接口示例**：写一个最小示例插件及其测试，演示注册条件、效果和动词；`mechanics/base.py` 的文档字符串写清可以/不可以修改什么。
5. 测试：插值、变体、随机（固定种子结果可预测）、错误剧本数据下不崩溃。

加分：撤销上一步（`undo`）；回合事件日志供调试。

GUI／网页优先必做：实现符合 `GameSession` 的真实会话适配、展示快照与插件动作描述。快照读取不改状态、不抽随机数；保存随机生成器状态或等价进度以支持继续回放。首个实现 PR 通过与测试替身相同的行为约定，并保留旧 Engine 调用。

### 4.3 ZRS：桌面／网页界面、命令解析、道具谜题插件

v0 的解析器、CLI 和道具插件继续保留。

必做：

1. Tkinter + ttk：剧本选择、正文、行动按钮、背包／线索、资源、存读档和结局页面；全程点击可通关。
2. 网页展示：`web/index.html`、`web/styles/`、`web/ui/` 使用相同快照样例，通过 ZC 的运行时桥接操作；适配桌面与手机宽度。
3. 道具插件提供结构化使用／组合动作、候选和说明；界面提交稳定 ID，规则继续由插件处理。
4. 中文长文、滚动、键盘焦点、窗口缩放、加载与错误恢复；动作串行，查看不扣资源。
5. 用测试替身独立测试页面，再与真实引擎和剧本集成；保留 CLI／解析器回归测试。

可选：复杂自然句式、拼写建议、终端颜色／换行、Tab 补全和逐字效果。新投入优先 GUI 与网页。

### 4.4 ZC：推理插件、剧本 A《雾港旧案》、整合与发布

v0 已有：线索获取与笔记、指认嫌疑人、按证据组合决定结局、线索与指认的校验；剧本 A 序章（8 个场景、4 条线索、3 个结局）。

必做：

1. **推理插件增强**（玩法借鉴剧本杀，见 [项目说明](project-brief.md)）：
   - 深入搜证：已发现的线索可再次调查得到下一级线索；
   - 审问：每个嫌疑人有话题列表，出示特定线索解锁新证词（可做成对话场景或插件命令 `问 周文 账本`）；
   - 分幕：线索按幕解锁，幕切换时有过场文字；
   - 指认需要说明理由：动机、手段、证据三项匹配度决定结局档次。
2. **剧本 A 扩写**（`story.json`）：15–20 个场景、3 名嫌疑人各有秘密、至少 1 条误导线索、至少 4 个结局；每个结局一个通关脚本。
3. **整合**：维护 `tests/integration/` 与 `main.py`，保证 `develop` 始终可运行；打包脚本放 `tools/`（生成 `groupX_project.zip`）。
4. 测试：每项新机制的单元测试；剧本 A 的通关脚本。

加分：游戏结束后显示线索关系图（哪条线索指向哪个嫌疑人），作为复盘。

GUI／网页新增必做：推理插件提供已发现线索、可展示人物与审问／指认动作；ZC 整合 `main.py` 和 VS Code 启动配置、`web/runtime/` 的 Pyodide 桥接、网页打包与 Cloudflare Git 自动发布。整合入口时保留 YHT 已合入的校验／场景图功能。

### 4.5 LQ：存档、通关回放与探索测试、剧本 B《深空回声》

v0 已有：JSON 存档（原子写入、剧本不匹配/损坏/字段缺失检测、剧本变更提示）、通关脚本回放、结局覆盖率；剧本 B 序章（6 个场景、氧气倒计时、道具组合、2 个结局、3 个通关脚本）。

必做：

1. **存档增强**：多个存档槽（`存档 2`）、自动存档、列出存档（时间、场景、回合）。
2. **随机探索测试**：从起点随机选择合法命令走 N 步，重复 M 次（固定种子可复现），断言不崩溃、每次都停在合法状态；两个剧本都纳入 CI。这是比手写测试更强的“程序不会崩溃”证据。
3. **剧本 B 扩写**（`story.json`）：8–12 个场景、两种资源（氧气与电量）、至少 3 个结局；用上 ZRS 的 `use A on B` 和 ZQO 的文本插值/随机事件；每个结局一个通关脚本。
4. 测试：存档槽、自动存档、随机探索本身的测试。

加分：`python main.py replay --all` 汇总所有剧本的覆盖率表格；用 `coverage` 统计行覆盖率（第三方工具只用于开发，不作为运行依赖）。

GUI／网页新增必做：分离存档数据编码／校验与存储；实现 `SaveStore`，提供桌面文件和浏览器持久化、JSON 导入导出；验证刷新恢复、损坏存档、跨端互通与确定性回放。

## 6 代码审查轮换

课程“卓越”等级要求文档与代码审查。每个 PR 至少一名其他成员审阅（可由其 AI 协助，审阅意见要本人确认），按轮换指定：

| 作者 | 审阅人 | 理由 |
| --- | --- | --- |
| YHT | ZC | ZC 的剧本最依赖格式与校验 |
| ZQO | YHT | 引擎读取 YHT 定义的模型 |
| ZRS | LQ | 回放工具直接调用解析器 |
| ZC | ZRS | 推理插件的命令要经过解析器 |
| LQ | ZQO | 存档与回放依赖引擎状态 |

审阅看三点：测试是否覆盖异常输入；是否改动了别人的文件或接口；文档是否同步。意见写在 PR 评论里，最终阶段作为“代码审查”的证据。

## 9 每人验收清单（模块阶段）

- [ ] 第 4 节本模块必做项已实现，`tests/<缩写>/` 单独运行通过，全部测试通过。
- [ ] 测试覆盖正常、边界、异常输入；无效输入不会让程序崩溃。
- [ ] 公开函数和类有文档字符串；改动接口的已按 [接口约定](contracts.md) 第 5 节走 contract PR。
