文件都在 `taleloom/` 下（`main.py` 与 `stories/` 在仓库根目录）。每人都有：一个可独立测试的代码模块、一组需求与测试、一页课堂幻灯片、一段视频、一份个人报告的素材。ZC 和 LJ 各写一个剧本，同时都是插件或测试工具的作者，剧本工作量用插件/工具量平衡；YHT、ZQO、ZRS 的模块是两个剧本共同依赖的底座。

## 2 架构与依赖方向

```text
             main.py（入口：play / validate / replay）
                 │
   ┌─────────────┼───────────────┐
 cli.py ◄─ parser.py         replay.py ─► save.py         ← ZRS / LJ
   │                             │
   └──────────► engine.py ◄──────┘                         ← ZQO
               │      │
         rules.py  state.py   mechanics/base.py            ← ZQO
               │                 ▲          ▲
               │        mystery.py      puzzle.py          ← ZC / ZRS
               ▼
  model.py ◄── loader.py   validator.py   walk.py          ← YHT
               ▲
       stories/*/story.json（剧本数据）                      ← ZC / LJ
```

依赖只向下：界面和工具调用引擎，引擎调用规则与插件，所有模块共享 `model.py` 中的数据类型。引擎不调用 `input`/`print`、不读写文件，所以能在单元测试中直接驱动。接口细节见 [接口约定](contracts.md)。

## 3 为什么五个人可以同时开工

上一个项目（SkyRoute）按棒次串行，后一棒要等前一棒合入。本项目改为**契约先行、并行开发**：

1. **v0 骨架已就绪**：仓库里已有可运行的最小引擎、两个剧本序章和 94 项测试，CI 全绿。每个模块都有能用的最小实现，没有“等别人先写完”的空接口。
2. **接口冻结在 `model.py` 和 `engine.Engine` 的公开方法上**。修改接口走 contract PR（[接口约定](contracts.md) 第 5 节），其余代码各改各的文件，不会冲突。
3. **测试互不牵连**：各模块测试只用 `tests/fixtures.py` 里的迷你剧本，不读真实剧本。剧本作者改剧情不会让别人的单元测试失败；剧本是否能通关由 `tests/integration/` 统一检查。
4. **CI 按成员分项显示**：PR 页面上 `tests (yht)`、`tests (zrs)` 等六项分别显示结果，一眼看出是哪个模块出错。

每人本地只跑自己的测试：

```bash
python -B -m unittest discover -s tests/<缩写小写> -t .
```

## 4 各成员任务

每项任务写入 [需求表](requirements.md)（需求编号 → 测试），先写测试再写实现（课件 V 模型 / TDD）。“必做”是满足课程“优良/卓越”所需；“加分”在必做完成后选做。

### 4.1 YHT：剧本格式、加载与静态校验

v0 已有：JSON 加载、带位置的格式错误（如 `$.scenes[1].text: 应为字符串`）、跳转/物品/未知条件效果检查、可达性与结局检查。

必做：

1. **剧本格式 v1 定稿**：完善 [剧本格式](story-format.md)，给每个字段写类型、是否必填、示例；写一页“剧本作者快速上手”。
2. **参数校验**：条件和效果的参数类型（如 `var` 必须是 `[名称, 运算符, 数值]`、运算符合法、`add_var` 数值为整数），错误信息指向具体位置。
3. **结构检查增强**：只能进不能出的场景（陷阱环）、`once` 选项用完后无路可走的场景、未被任何地方使用的物品（警告）。
4. **校验命令的可读输出**：错误按场景分组，给出修改建议。
5. 测试：每条校验规则至少一个通过例和一个失败例。

加分：`python main.py graph <剧本>` 导出 Mermaid 场景图（演示用，能直观展示两个剧本的结构差异）；JSON 解析错误显示出错行内容。

演示素材：同一个错误剧本，`validate` 一次列出所有问题——“剧本作者不用跑游戏就知道哪里写错”。

### 4.2 ZQO：运行时核心与插件接口；总体架构

v0 已有：状态、条件/效果注册表、选择与跳转、一次性/条件选项、每回合效果与触发器、跳转循环检测、插件动词分发。

必做：

1. **文本插值**：场景文字中的 `{vars.oxygen}`、`{item:tape}` 等占位符在显示时替换，未知占位符给出清楚提示而不是崩溃。
2. **条件化场景文字**：场景可声明 `variants`（满足条件时追加或替换描述），让同一地点前后两次进入看到不同内容。
3. **可复现的随机**：`{"chance": 30}` 条件，随机种子保存在 `GameState` 中，读档和回放结果一致（LJ 的回放测试依赖这一点）。
4. **插件接口文档**：在 [接口约定](contracts.md) 中写清插件生命周期、可以/不可以修改什么；写一个最小示例插件的测试。
5. **总体架构**：架构图与一次命令的处理时序（输入 → 解析 → 引擎 → 规则/插件 → 输出），供报告和第 1 页幻灯片使用。
6. 测试：插值、变体、随机（固定种子结果可预测）、错误剧本数据下不崩溃。

加分：撤销上一步（`undo`）；回合事件日志供调试。

演示素材：讲“为什么做引擎”——同一套核心跑两个剧本，插件不改核心。

### 4.3 ZRS：命令解析、命令行界面、道具谜题插件

v0 已有：全角/半角统一、中英文动词别名、编号与选项文字匹配、中文动词无空格识别、`使用`/`组合` 两个道具命令、可注入输入输出的 CLI。

必做：

1. **更自然的句式**：“把扳手用在面板上”“use wrench on panel” → `use` 带两个参数；“看看胶带”“检查 X” → 查看物品说明。
2. **容错与提示**：输入有歧义时列出候选（“你是指：1. 去后厨 2. 回到大堂？”）；拼写接近时给建议（标准库 `difflib`）。
3. **界面易用性**：状态栏（回合数、剧本声明需显示的变量如氧气）、中英文混排按显示宽度自动换行（`unicodedata.east_asian_width`）、可关闭的颜色（`--no-color`）、首次进入显示简短操作说明。
4. **道具插件增强**：`use A on B`（B 为场景中的对象或另一件物品）、物品说明、组合失败时的提示文本可由剧本自定义。
5. **可用性测试**：请 3–5 名组外同学试玩，记录卡住的地方和修改（课程“可用性 10%”的证据），写入 [测试报告](testing.md)。
6. 测试：每种句式的解析、歧义、无效输入不崩溃（课程“错误处理”）、CLI 脚本化输入。

加分：命令历史与 Tab 补全（`readline`，注意 Windows 兼容）；逐字打印效果（可关闭）。

演示素材：现场输入几种不同说法都能被理解；乱输入时程序给提示不崩溃。

### 4.4 ZC：推理插件、剧本 A《雾港旧案》、整合与发布

v0 已有：线索获取与笔记、指认嫌疑人、按证据组合决定结局、线索与指认的校验；剧本 A 序章（8 个场景、4 条线索、3 个结局）。

必做：

1. **推理插件增强**（玩法借鉴剧本杀，见 [项目说明](project-brief.md)）：
   - 深入搜证：已发现的线索可再次调查得到下一级线索；
   - 审问：每个嫌疑人有话题列表，出示特定线索解锁新证词（可做成对话场景或插件命令 `问 周文 账本`）；
   - 分幕：线索按幕解锁，幕切换时有过场文字；
   - 指认需要说明理由：动机、手段、证据三项匹配度决定结局档次。
2. **剧本 A 扩写**：15–20 个场景、3 名嫌疑人各有秘密、至少 1 条误导线索、至少 4 个结局；每个结局一个通关脚本。
3. **整合与发布**：维护 `tests/integration/` 与 `main.py`；每周把 `develop` 合成一个可演示版本；最终打包 `groupX_project.zip`（打包脚本放 `tools/`），在干净环境按 README 复现。
4. 测试：每项新机制的单元测试；剧本 A 的通关脚本。

加分：线索关系图（哪条线索指向哪个嫌疑人）在游戏结束后显示，作为复盘。

演示素材：录屏演示剧本 A 完整推理链；讲两个剧本如何只靠配置不同就共用一个引擎。

### 4.5 LJ：存档、通关回放与测试报告、剧本 B《深空回声》

v0 已有：JSON 存档（原子写入、剧本不匹配/损坏/字段缺失检测、剧本变更提示）、通关脚本回放、结局覆盖率；剧本 B 序章（6 个场景、氧气倒计时、道具组合、2 个结局、3 个通关脚本）。

必做：

1. **存档增强**：多个存档槽（`存档 2`）、自动存档、列出存档（时间、场景、回合）。
2. **随机探索测试**：从起点随机选择合法命令走 N 步，重复 M 次，断言不崩溃、每次都停在合法状态；记录发现的剧本问题。这是比手写测试更强的“程序不会崩溃”证据。
3. **测试报告** [testing.md](testing.md)：按课件 V 模型整理需求 → 测试对应、各模块测试数量与覆盖情况、CI 截图、随机探索结果、可用性测试结果（与 ZRS 合作）。
4. **剧本 B 扩写**：8–12 个场景、两种资源（氧气与电量）、至少 3 个结局；用上 ZRS 的 `use A on B` 和 ZQO 的文本插值/随机事件；每个结局一个通关脚本。
5. 测试：存档槽、自动存档、随机探索本身的测试。

加分：`python main.py replay --all` 汇总所有剧本的覆盖率表格；用 `coverage` 统计行覆盖率（第三方工具只用于开发，不作为运行依赖，报告中注明）。

演示素材：讲测试体系——单元测试、通关回放、随机探索、CI 按成员分项；现场改坏一个剧本，CI 立刻报错。

## 6 代码审查轮换

课程“卓越”等级要求文档与代码审查。每个 PR 至少一名其他成员审阅（可由其 AI 协助，审阅意见要本人确认），按轮换指定：

| 作者 | 审阅人 | 理由 |
| --- | --- | --- |
| YHT | ZC | ZC 的剧本最依赖格式与校验 |
| ZQO | YHT | 引擎读取 YHT 定义的模型 |
| ZRS | LJ | 回放工具直接调用解析器 |
| ZC | ZRS | 推理插件的命令要经过解析器 |
| LJ | ZQO | 存档与回放依赖引擎状态 |

审阅看三点：测试是否覆盖异常输入；是否改动了别人的文件或接口；文档是否同步。意见写在 PR 评论里，作为报告中“代码审查”的证据。

| 页 | 成员 | 内容 |

| 5 | LJ | 质量：测试体系、CI、AI 辅助开发；结论 |

**视频（≤ 15 分钟）**，按课程要求的“引言、问题、技术方法、演示、结论”：

| 时段 | 内容 | 负责 |
| --- | --- | --- |
| 0:00–2:00 | 引言、问题、架构 | ZQO |

| 4:00–6:00 | 交互与错误处理 | ZRS |
